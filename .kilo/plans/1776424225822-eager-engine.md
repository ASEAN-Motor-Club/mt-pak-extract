# Anti-Cheat Vanilla Guard Mod — Feasibility Analysis & Implementation Plan

## Requirements

- **Server control**: Yes (you run the MotorTown server)
- **Threat model**: PAK mods + Cheat Engine (runtime memory editing)
- **Policy**: Pure vanilla only (no other mods allowed)
- **Goal**: Ensure multiplayer clients have unmodified game data

## Verdict: FEASIBLE with Hybrid PAK + UE4SS + Server Architecture

The PAK-only approach has fatal weaknesses (see below), but combining it with UE4SS runtime validation + server-side enforcement creates a robust multi-layer defense. Since you control the server, you can **deny multiplayer access** to clients that fail validation — this is the enforcement mechanism that makes the entire system work.

---

## Feasibility Breakdown

### 1. Building the PAK (FEASIBLE)

Creating a mod PAK with vanilla DataTables + 1 marker part is fully supported by the existing toolchain:

- Extract base game DataTables via the pipeline (already done in `out/`)
- Add 1 invisible marker row to `VehicleParts0` using `--add-rows` (clone from existing row, set `bIsHidden: true`, `Cost: 0`, `MassKg: 0`)
- Package into `zzz_ASEAN_VanillaGuard_P.pak` using `mod_pack`

The game already has hidden parts (e.g., `I6Sport_200HP` engine, `Crany` wheel with `is_hidden: true`), confirming the engine supports invisible parts.

**Estimated DataTables to include** (to cover all cheat vectors):
| DataTable | Rows | Risk if not included |
|-----------|------|---------------------|
| VehicleParts0 | 50 | Tire/engine/LSD/bulletproof tire cheats |
| VehicleParts | 713 | Part cost/mass/physics cheats |
| Engines | varies | Engine power cheats |
| Transmissions | varies | Transmission cheats |
| AeroParts | varies | Aero/downforce cheats |
| LSD | varies | Differential cheats |
| BrakePads | varies | Brake cheats |
| BrakePower | varies | Brake power cheats |
| BrakeBalance | varies | Brake balance cheats |
| Suspensions | varies | Suspension cheats |
| Wheels | varies | Wheel cheats |
| Headlights | varies | Headlight cheats |
| FinalDriveRatio | varies | Gear ratio cheats |
| Horn | varies | Minor (horn changes) |
| UtilityParts | varies | Siren/utility cheats |
| Cargos | ~100 | Cargo weight/value cheats |
| Cargos_01 | varies | Cargo variant cheats |
| Vehicles* | varies | Vehicle stat cheats |
| Decals | ~423 | Minor (decal cheats) |

**~20+ DataTable files** need to be included. This PAK would be significantly larger than typical mods.

### 2. Alphabetical Override Enforcement (WEAK)

UE5 loads `_P.pak` files in **strict alphabetical order**, last one wins per-file. This is the core enforcement mechanism.

**Problems:**

| Attack | Difficulty | Mitigation? |
|--------|-----------|-------------|
| Player renames another mod to `zzzz_*` | Trivial | None within UE5 |
| Player doesn't install the guard mod | Trivial | None within UE5 |
| Mod author ships a mod named `zzzzz_*` | Trivial | None within UE5 |
| Player modifies the guard PAK itself (remove it from load) | Trivial | None within UE5 |
| Player repacks the guard PAK with modified DataTables + marker | Moderate | Detection possible if checking row counts/checksums |

The `zzz_` prefix is a **social convention**, not a technical enforcement. Any motivated cheater can trivially bypass it.

### 3. Marker Part Detection (PROBLEMATIC)

The critical question: **How do you scan for the marker part?**

#### Option A: In-game detection (checking if a player HAS the part equipped)
- UE5/MotorTown has no built-in mechanism for servers to query client part inventories
- You'd need custom game code (Blueprint or C++) to:
  - Check `VehicleParts0` for the marker row at runtime
  - Report its presence/absence to a server
- **Problem**: Client-side code is in the PAK → the same PAK being overridden. A cheater can skip the check.

#### Option B: Out-of-band verification (external tool)
- A launcher/validator tool that:
  - Scans the `Paks/` directory for the guard PAK
  - Verifies its contents (checksum specific DataTables)
  - Launches the game only if valid
- **Problem**: Players can bypass the launcher. No kernel-level enforcement.

#### Option C: Server-side validation
- Server checks client state during multiplayer sessions
- Compare vehicle physics/performance against expected values
- **Problem**: MotorTown's server infrastructure (if any) likely doesn't support this. UE5 dedicated servers can validate some replication data but not arbitrary DataTable contents.

#### Option D: Filesystem checksum verification
- Compute SHA256 of key DataTable `.uasset` files at game startup
- Compare against known-good checksums
- **Problem**: Checksum logic must run on the client → spoofable. Would need to be in a compiled C++ module, not a Blueprint.

### 4. Coverage Gaps (CRITICAL — PAK Alone Insufficient)

The PAK guard alone does NOT cover:

| Cheat Vector | PAK Covers? | UE4SS Covers? | Server Covers? |
|-------------|-------------|---------------|----------------|
| DataTable modifications (parts, cargos, vehicles) | YES (if loads last) | YES (row count check) | YES (heartbeat) |
| Blueprint CDO patches (horn, stats, properties) | **NO** | **YES** (CDO property check) | **YES** (anomaly detect) |
| New assets (cargo blueprints, tire physics) | **NO** | **YES** (object enumeration) | **YES** (anomaly detect) |
| Cheat Engine / memory editors | **NO** | **PARTIAL** (can re-read values) | **YES** (telemetry validation) |
| Player removes guard PAK | **NO** | **YES** (marker missing) | **YES** (no heartbeat = kick) |
| Player renames cheat PAK after guard | **NO** | **YES** (row count mismatch) | **YES** (heartbeat violation) |

**Key insight**: The PAK is just Layer 1. UE4SS + server validation are essential for coverage.

### 5. Cheat Engine Detection (PAK Cannot Help)

Cheat Engine modifies **runtime memory** after assets are loaded. The PAK guard does nothing against this. Detection strategies:

| Strategy | How It Works | Bypass Difficulty |
|----------|-------------|-------------------|
| Periodic CDO re-read | UE4SS re-reads vehicle CDO properties every N seconds, compares against expected | Moderate — CE can re-modify after each check |
| Physics monitoring | Hook speed/accel UFunctions, compare against theoretical max per vehicle | Hard — requires understanding expected physics |
| Server-side telemetry | Server receives speed/position data, flags impossible values | Very hard — server-side, can't be bypassed by CE |
| Checksum critical memory | UE4SS computes rolling hash of CDO property blocks, compares against baseline | Hard — requires reverse engineering to know which memory to re-hash |

**Recommendation**: UE4SS does periodic CDO re-reads + hooks physics functions. Server validates telemetry as ground truth. CE user can spoof UE4SS reads but server catches impossible physics.

## Alternative Approaches

### A. Server-Side Physics Validation (Strongest)

Instead of trying to enforce client-side PAK integrity, validate behavior server-side:

- Monitor vehicle telemetry (speed, acceleration, grip) during multiplayer
- Flag anomalies against expected physics ranges per vehicle model
- Server authoritative physics (UE5 supports this with `bReplicateMovement`)

**Pros**: Cannot be bypassed client-side. Covers ALL cheat types (memory editing, PAK mods, etc.)
**Cons**: Requires server access and custom game code. Higher implementation cost.

### B. Checksum-Based Whitelist (Moderate)

- Compute checksums of all critical `.uasset` files at game launch
- Submit checksums to a validation server
- Server maintains whitelist of known-good checksums (vanilla + approved mods)
- Block multiplayer if checksums don't match any known-good set

**Pros**: Covers DataTables AND blueprints AND any file. Can support approved mods.
**Cons**: Client-side checksum code is spoofable. Requires server infrastructure. Per-version checksum maintenance.

### C. Minimal Marker + Social Trust (Simplest)

- Create a small mod that ONLY adds the marker part (1 row in VehicleParts0)
- Don't try to enforce vanilla gameplay via overrides
- Use the marker as a **voluntary compliance signal** — communities can require it for events/leagues
- Combine with streaming/SS proof for competitive play

**Pros**: Minimal maintenance. Compatible with other mods. No false positives.
**Cons**: No enforcement. Purely honor system. Easy to fake.

### D. Compat-Mod Architecture (Cooperative)

- Instead of overriding all other mods, build your mod as a compat layer
- `--compat-mod` system already exists — extract DataTables from other mods, validate them
- Ship an "approved mods" list with validated checksums
- Your mod extracts each installed mod's DataTables, checks against approved versions
- If unapproved mods detected, the marker part is removed → detection fails

**Pros**: Allows legitimate mods. Detects modifications to approved mods.
**Cons**: Complex. Still client-side. Doesn't cover blueprint CDO patches or new assets.

## UE4SS-Based Anti-Cheat (Better Than PAK Approach)

UE4SS is a Lua scripting system that injects into UE4/5 games at runtime. It provides **runtime inspection of actual loaded game state**, which is fundamentally more powerful than the PAK-based approach that only controls static file overrides.

### Why UE4SS Is Better

| Capability | PAK Guard | UE4SS |
|-----------|-----------|-------|
| Validate loaded DataTable row counts | No (can only provide override) | **Yes** — `FindObject` + read `Data` array |
| Validate specific row values | No | **Yes** — iterate rows, check property values |
| Detect blueprint CDO modifications | No | **Yes** — `GetCDO()` + read CDO properties |
| Detect new assets not in vanilla | No | **Yes** — `ForEachUObject` + compare against whitelist |
| Report to a server | No | **Yes** — `ExecuteAsync` with HTTP requests |
| Monitor vehicle performance in real-time | No | **Yes** — hook physics UFunctions |
| Enforce load order | No (alphabetical only) | **Yes** — can check what's actually loaded |
| Tamper-proof | No (PAKs easily replaced) | **Partially** (scripts readable, but C++ mods harder to reverse) |

### UE4SS Anti-Cheat Architecture

```
┌─────────────────────────────────────────────────┐
│ UE4SS Lua Script (runs in game process)         │
│                                                 │
│  1. On game load:                               │
│     - FindObject("VehicleParts0")              │
│     - Count rows → compare against known count  │
│     - Validate marker row exists with correct   │
│       values (Cost=0, bIsHidden=true, etc.)     │
│     - ForEachUObject → build inventory of all   │
│       loaded DataTables, compare against        │
│       expected set                              │
│                                                 │
│  2. Periodic checks:                             │
│     - Hook vehicle physics UFunctions           │
│     - Monitor speed/accel against expected      │
│       ranges per vehicle type                   │
│     - Check for unexpected new cargo/part       │
│       objects at runtime                        │
│                                                 │
│  3. Report to server:                            │
│     - ExecuteAsync HTTP POST with:              │
│       { player_id, row_counts, checksums,       │
│         vehicle_telemetry, violations[] }       │
│     - Server validates → allow/deny multiplayer  │
│                                                 │
│  4. Marker part verification:                    │
│     - PAK still adds marker row to              │
│       VehicleParts0 (as "proof of install")     │
│     - UE4SS validates the row is actually        │
│       loaded in memory, not just in the file    │
└─────────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────────┐
│ Validation Server                                │
│                                                  │
│  - Receives client validation reports           │
│  - Compares against per-version expected values  │
│  - Flags anomalies (row count mismatch,         │
│    unknown objects, physics outliers)            │
│  - Maintains approved-mod whitelist             │
│  - Issues session tokens for multiplayer        │
└─────────────────────────────────────────────────┘
```

### What UE4SS Can Validate At Runtime

**1. DataTable Integrity**
```lua
-- Find the loaded VehicleParts0 DataTable
local vp0 = FindObject("DataTable", nil, "VehicleParts0")
if not vp0 then
    ReportViolation("VehicleParts0 not found")
    return
end

-- Check row count (should be 50 for vanilla + 1 marker = 51)
local rowData = vp0.RowStruct  -- access row data
local rowCount = rowData:GetArrayNum()
if rowCount ~= EXPECTED_ROW_COUNT then
    ReportViolation("VehicleParts0 row count: " .. rowCount .. " expected: " .. EXPECTED_ROW_COUNT)
end
```

**2. Marker Part Verification**
```lua
-- Find the marker row in the loaded DataTable
local markerRow = FindObject("StructProperty", nil, "ASEAN_VanillaGuard_Marker")
if not markerRow then
    ReportViolation("Marker part not found in loaded data")
end
-- Verify marker values haven't been tampered with
```

**3. Blueprint CDO Validation**
```lua
-- Check a vehicle's CDO for suspicious property overrides
local vehicleClass = StaticFindObject("/Game/Cars/Models/Jemusi/BP_Jemusi.Default__BP_Jemusi_C")
if vehicleClass then
    local cdo = vehicleClass:GetCDO()
    local maxSpeed = cdo.MaxSpeed  -- read actual runtime value
    if maxSpeed > EXPECTED_MAX_SPEED then
        ReportViolation("Jemusi MaxSpeed modified: " .. maxSpeed)
    end
end
```

**4. Vehicle Performance Monitoring**
```lua
-- Hook physics functions to detect impossible values
RegisterHook("/Script/MotorTown.MTVehicle:GetCurrentSpeed", function(self, ...)
    local speed = self:GetCurrentSpeed()
    if speed > MAX_POSSIBLE_SPEED then
        ReportViolation("Impossible speed: " .. speed)
    end
end)
```

### UE4SS Limitations

| Limitation | Impact | Mitigation |
|-----------|--------|-----------|
| Lua scripts are plaintext/readable | Attacker can see validation logic | Use C++ UE4SS mod instead of Lua (compiled, harder to reverse) |
| Player can disable UE4SS via `--disable-ue4ss` | Validation never runs | Server requires validation heartbeat — no report = kicked |
| Player can modify UE4SS scripts | Validation can be bypassed | C++ mod + server-side validation as fallback |
| UE4SS itself could be replaced | Malicious UE4SS that sends fake data | Server validates telemetry anomalies, not just client reports |
| Requires Windows | UE4SS is Windows-only | MotorTown is Windows-only, so no issue |

### C++ UE4SS Mod (Stronger Than Lua)

UE4SS also supports **C++ mods** (`cppmods/` directory), which are compiled DLLs. These are significantly harder to reverse than plaintext Lua scripts:

- Validation logic is in compiled native code
- Cannot be trivially edited like Lua scripts
- Can implement cryptographic checksums (SHA256 of loaded asset data)
- Can hook at a lower level than Lua

## Recommended Architecture: Hybrid PAK + UE4SS

The strongest approach combines both:

### Layer 1: PAK Mod (Marker + Vanilla Override)
- Contains vanilla DataTables + 1 invisible marker part
- Named `zzz_ASEAN_VanillaGuard_v{version}_P.pak` for alphabetical priority
- Provides the **file-level** override and the marker row
- **Purpose**: Deters casual cheaters, provides the marker signal

### Layer 2: UE4SS Script/C++ Mod (Runtime Validation)
- Validates that the marker row is actually loaded in memory
- Validates DataTable row counts match expected vanilla + marker
- Validates vehicle CDO properties against expected ranges
- Monitors vehicle performance for physics anomalies
- Reports validation results to server on heartbeat
- **Purpose**: Catches sophisticated cheaters who bypass the PAK override

### Layer 3: Server Validation (Ground Truth)
- Requires periodic validation heartbeat from UE4SS mod
- No heartbeat → player kicked from multiplayer
- Validates telemetry against expected ranges
- Maintains per-version expected values database
- Can cross-validate with `motortown.db` data
- **Purpose**: Only layer that cannot be client-side bypassed

### How They Work Together

```
Casual cheater → PAK override blocks DataTable mods → CAUGHT
PAK bypass cheater → UE4SS detects row count mismatch → CAUGHT
UE4SS bypass cheater → No heartbeat to server → KICKED
Memory hacker → Server detects physics anomaly → CAUGHT
```

## Implementation Plan

### Phase 1: PAK Guard Mod (Use Existing Toolchain)

The PAK guard serves as **Layer 1 defense** — a vanilla override + marker signal. It blocks casual PAK-based cheats and provides the marker row that UE4SS validates.

**Step 1.1**: Create marker part definition
- Invisible `Attachment`-type row in VehicleParts0
- `bIsHidden: true`, `Cost: 0`, `MassKg: 0`
- `GameplayTags: ["Part.VanillaGuard"]`
- Row name: `ASEAN_VanillaGuard_Marker`

**Step 1.2**: Create `scripts/create_vanillaguard.py`
- Subclass `ModBuilder`
- `register_in_tables()`: `--add-rows` marker row to VehicleParts0
- `assemble_pak()`: Stage ALL critical DataTable `.uasset`/`.uexp` from `out/` + modified VehicleParts0
- Include ~20 DataTables (see table in Section 1)

**Step 1.3**: Build the PAK
- `zzz_ASEAN_VanillaGuard_v{version}_P.pak`
- Rebuild automatically via `new-version.sh`

**Files to create/modify**:
- `scripts/create_vanillaguard.py` — new build script
- `vanillaguard_marker.json` — `--add-rows` config for marker row

### Phase 2: UE4SS Validation Script (New Code — Client-Side)

The UE4SS mod is **Layer 2** — runtime validation that checks what's actually loaded in memory.

**Step 2.1**: Create UE4SS mod structure
```
MotorTown/Binaries/Win64/Mods/VanillaGuard/
├── enabled.txt
├── scripts/
│   └── main.lua
```

**Step 2.2**: Implement validation in `main.lua`

Core validation checks (run on game load + every 30s):

```lua
-- 1. MARKER CHECK: Verify guard PAK is loaded
local function check_marker()
    local vp0 = StaticFindObject("/Game/DataAsset/VehicleParts/VehicleParts0.VehicleParts0")
    if not vp0 then return false, "VehicleParts0 not found" end
    -- Check for marker row by enumerating DataTable rows
    -- Verify Cost=0, bIsHidden=true, row name matches
end

-- 2. ROW COUNT CHECK: All critical DataTables have expected row counts
local function check_row_counts(expected)
    for _, tbl in ipairs(CRITICAL_TABLES) do
        local dt = StaticFindObject(tbl.path)
        local count = dt.RowMap:GetArrayNum()  -- actual loaded count
        if count ~= expected[tbl.name] then
            return false, tbl.name .. " count: " .. count .. " expected: " .. expected[tbl.name]
        end
    end
    return true
end

-- 3. CDO CHECK: Vehicle blueprints have unmodified properties
local function check_vehicle_cdos()
    for _, v in ipairs(MONITORED_VEHICLES) do
        local cdo = StaticFindObject(v.path):GetCDO()
        local maxSpeed = cdo.MaxSpeed
        if maxSpeed > v.expected_max_speed then
            return false, v.name .. " MaxSpeed modified"
        end
    end
    return true
end

-- 4. PHYSICS MONITOR: Hook vehicle speed, detect impossible values
RegisterHook("/Script/MotorTown.MTVehicle:GetForwardSpeed", function(self)
    local speed = self:GetForwardSpeed()
    if math.abs(speed) > MAX_REASONABLE_SPEED then
        report_violation("impossible_speed", speed)
    end
end)

-- 5. HEARTBEAT: Report validation status to server
LoopAsync(30000, function()
    local valid, reason = run_all_checks()
    local payload = json.encode({
        player_id = get_player_id(),
        game_version = get_game_version(),
        valid = valid,
        reason = reason,
        timestamp = os.time()
    })
    -- HTTP POST to validation server
    ExecuteAsync(function()
        -- Use os.execute or custom HTTP to POST payload
    end)
    return false  -- never stop the loop
end)
```

**Step 2.3**: Generate `expected_values.lua` from pipeline

New script: `scripts/generate_validation_rules.py`
- Reads `motortown.db` for row counts per DataTable
- Reads `out/*_parsed.json` for vehicle CDO property ranges
- Outputs Lua table definitions with expected values
- Run automatically after `new-version.sh`

### Phase 3: Server Validation (Infrastructure — You Run the Server)

The server is **Layer 3** — the ground truth that cannot be bypassed client-side.

**Step 3.1**: Validation server (simple HTTP API)

```
POST /api/validate
  Body: { player_id, game_version, valid, reason, timestamp, row_counts, telemetry }
  Response: { session_token, next_check_seconds }

POST /api/telemetry
  Body: { player_id, session_token, vehicle_id, speed, accel, position }
  Response: { ok, violations[] }

GET /api/expected/{game_version}
  Response: { row_counts, cdo_ranges, max_speeds, ... }
```

**Step 3.2**: Server-side enforcement on your MotorTown server

Since you control the server:
1. **Require UE4SS heartbeat**: Client must POST `/api/validate` every 30s
2. **No heartbeat = kick**: If no validation received within 60s, disconnect player
3. **Validation failure = kick**: If `valid: false`, disconnect immediately
4. **Telemetry anomaly = kick**: If vehicle speed exceeds theoretical max, disconnect

**Step 3.3**: Expected values database

Server stores per-game-version expected values (generated from `motortown.db`):
- DataTable row counts
- Vehicle CDO property ranges (max speed, horsepower, etc.)
- Tire physics parameter ranges (friction, grip, etc.)
- Cargo weight ranges

**Step 3.4**: Cheat Engine detection via server telemetry

The server receives vehicle telemetry and validates against physics:

```python
def validate_telemetry(self, report):
    vehicle = get_vehicle_specs(report.vehicle_id, report.game_version)
    if report.speed > vehicle.theoretical_max_speed * 1.05:  # 5% tolerance
        return Violation("impossible_speed", report.speed, vehicle.theoretical_max_speed)
    if report.accel > vehicle.theoretical_max_accel * 1.10:  # 10% tolerance
        return Violation("impossible_accel", report.accel, vehicle.theoretical_max_accel)
```

This catches CE users who modify `MaxSpeed` or `HorsePower` in memory — the vehicle goes faster than physics allow, and the server detects it.

### Phase 4: C++ UE4SS Mod (Optional Hardening)

If Lua scripts are too easy to tamper with:

- Convert validation logic to compiled C++ mod in `cppmods/`
- Compute SHA256 of loaded DataTable binary data in memory
- Compare against expected checksums from server
- Harder to reverse-engineer than plaintext Lua
- Can hook deeper engine functions (memory allocation, asset loading)

### Version Management (All Phases)

| Phase | Auto-Rebuild Trigger | Output |
|-------|---------------------|--------|
| 1 PAK | `new-version.sh` | `zzz_ASEAN_VanillaGuard_v{ver}_P.pak` |
| 2 UE4SS | `scripts/generate_validation_rules.py` after pipeline | `expected_values.lua` |
| 3 Server | Upload `motortown.db` + expected values | Server config update |

### Deployment Flow for Players

1. Player downloads `zzz_ASEAN_VanillaGuard_v{ver}_P.pak` → installs in `Paks/`
2. Player installs UE4SS + VanillaGuard mod → in `Binaries/Win64/Mods/`
3. Player launches game → UE4SS validates + starts heartbeat to server
4. Player joins server → server checks for valid session token
5. Periodic: UE4SS sends heartbeat + telemetry → server validates
6. Violation → server kicks player from multiplayer

### Attack Tree & Defense Mapping

```
Attacker
├── Install cheat PAK mod
│   ├── PAK loads before guard PAK → Guard PAK overrides → CAUGHT (Layer 1)
│   └── PAK named zzzz_* loads after guard → UE4SS detects row count mismatch → CAUGHT (Layer 2)
├── Modify blueprint CDO via PAK
│   └── UE4SS CDO check detects modified properties → CAUGHT (Layer 2)
├── Use Cheat Engine
│   ├── Modify vehicle stats in memory
│   │   ├── UE4SS periodic CDO re-read detects change → CAUGHT (Layer 2)
│   │   └── CE re-modifies after each check → Server detects impossible speed → CAUGHT (Layer 3)
│   ├── Freeze UE4SS heartbeat
│   │   └── No heartbeat → Server kicks → CAUGHT (Layer 3)
│   └── Modify UE4SS Lua script
│       ├── Validation removed → Server detects no proper heartbeat format → CAUGHT (Layer 3)
│       └── Fake valid heartbeat → Server detects impossible telemetry → CAUGHT (Layer 3)
├── Remove guard PAK
│   └── UE4SS marker check fails → Validation fails → CAUGHT (Layer 2)
└── Remove UE4SS entirely
    └── No heartbeat to server → Server kicks → CAUGHT (Layer 3)
```

### Remaining Vulnerabilities

| Vulnerability | Difficulty | Impact |
|-------------|-----------|--------|
| CE user who only tweaks values within expected ranges (e.g., slight tire grip increase) | Moderate | Server telemetry may not detect 5-10% tweaks |
| Custom C++ mod that perfectly emulates valid heartbeat with fake data | Very High | Server telemetry cross-validation mitigates |
| Colluding players who share valid session tokens | High | Token binding to IP/machine ID mitigates |
| Game update lag — server expected values not updated yet | Low | Temporary — rebuild pipeline fixes |

### Recommended Priority

1. **Start with Phase 1 + Phase 3** (PAK guard + server enforcement): This immediately catches PAK mod cheaters and provides the server enforcement backbone
2. **Add Phase 2** (UE4SS): This catches CDO modifications and provides the marker verification
3. **Phase 4** (C++ mod): Only if Lua scripts are being tampered with in practice
